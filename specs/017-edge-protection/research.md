# Research: Edge protection & media caching (017, lot 1)

Phase 0 of `/speckit-plan`. Pre-spec research lives in
`docs/cdn-cache-exploration.fr.md`; this file records the planning decisions,
each with rationale and rejected alternatives. Facts about the codebase were
read on 2026-10-09; facts about Cloudflare, Caddy and Payload were checked
against their docs/source the same day (sources at the end).

---

## R1 — Cloudflare zone and plan

**Decision**: Move the `example.com` DNS zone (today at GoDaddy,
`ns*.domaincontrol.com`) to Cloudflare as a **full setup** on the **Free**
plan. Copy every existing record first (MX, SPF, DKIM/DMARC and Brevo sender
records, any verification TXT), import with proxy **off**, verify mail, then
switch nameservers. Hosts are turned to "proxied" one at a time later (R18).

**Rationale**: Partial (CNAME) setup is Business+ only. Free gives unmetered
DDoS mitigation, 5 custom WAF rules, 1 rate-limiting rule, the Free managed
ruleset, cache rules, Vary support (since 2026-09-22), all purge methods
(since 2025-04) and Authenticated Origin Pulls. Move to Pro (~20 $/month) on
the trigger documented in the deploy guide (spec Clarifications Q3).

**Alternatives**: Bunny (CNAME only, no L7 protection worth the name — ruled
out once anti-attack became mandatory); Cloudflare Business for partial setup
(cost, no need once the zone can move).

## R2 — Client domains: Cloudflare for SaaS on `www.`

**Decision**: Enable Cloudflare for SaaS on the zone. Create:
- a **fallback origin** `saas-origin.example.com` (proxied A/AAAA
  → VPS);
- a **CNAME target** `sites.example.com` that clients point their
  `www.` at;
- one **custom hostname** per client `www.` host, edge certificate validated by
  **HTTP DCV** (automatic once the client's CNAME exists).

The client's root redirects permanently to `www.` through the client
registrar's forwarding (GoDaddy now forwards over HTTPS). Path and query
preservation MUST be verified per registrar (quickstart V9) because already
sent opt-in/unsubscribe emails link to root URLs; if a registrar drops the
path, that client falls back to moving their zone into Trefle's account
(spec Q1 option A, for that client only).

**Rationale**: Clients keep their DNS; one CNAME onboards them. 100 custom
hostnames are included on non-Enterprise plans, then 0.10 $/month each.
Apex proxying is Enterprise-only, hence `www.` (spec Q1).

**Facts that shape the next decisions**: with the default (fallback) origin,
Cloudflare sends **Host and SNI = the custom hostname** to the origin, so the
origin needs a certificate valid for `www.client.tld` under Full (strict)
(R3). Global/zone AOP applies to custom hostnames on the zone (R4).

## R3 — Origin certificates under Full (strict): ACME DNS-01 with delegation

**Decision**: SSL mode **Full (strict)** zone-wide. Caddy obtains every origin
certificate (Trefle hosts and client `www.` hosts) with **ACME DNS-01** via the
`caddy-dns/cloudflare` module, using **CNAME delegation**: each host has
`_acme-challenge.<host> CNAME acme-delegate.example.com`, and Caddy
writes the TXT at that name (`dns_challenge_override_domain`). For client
hosts this is the second DNS record they add at onboarding.

This needs a **custom Caddy image** (`xcaddy build --with
github.com/caddy-dns/cloudflare`), built from `infra/caddy/Dockerfile`, with a
Cloudflare API token scoped to *Zone → DNS → Edit* on this zone only.

**Rationale**: Works identically for our hosts and client hosts, does not
depend on HTTP traffic reaching the origin (so port 80 can be closed), and is
unaffected by Cloudflare's own HTTP DCV for edge certificates (which uses the
HTTP path, not `_acme-challenge`).

**Alternatives**:
- *Cloudflare Origin CA certificate* — only covers hostnames of our own zone,
  not client domains.
- *HTTP-01 through the proxy* — depends on how Cloudflare forwards
  `/.well-known/acme-challenge/` for custom hostnames whose edge certificate
  it validates the same way; fragile, and keeps port 80 open.
- *Full (non-strict) for custom hostnames via a Configuration Rule* — keeps
  encryption but Cloudflare would not verify the origin; contradicts FR-004.
  Kept as the documented emergency fallback if DNS-01 delegation is blocked.
- *SNI rewrite / host header override* — entitlement via account team
  (Enterprise).

## R4 — Origin lock-down (FR-002, FR-003)

**Decision**: three layers.
1. **Network**: the Hostinger VPS firewall (hPanel, applied outside the VM)
   allows 443 only from Cloudflare's published IPv4/IPv6 ranges; 80 closed;
   22 unchanged. *Not* `ufw` alone: Docker-published ports bypass `ufw`'s
   INPUT rules.
2. **Account-exclusive authentication**: **zone-level Authenticated Origin
   Pulls with our own certificate** (generated by
   `infra/cloudflare/aop-cert.sh`, uploaded once). Caddy requires and verifies
   the client certificate on every site (`tls { client_auth { mode
   require_and_verify; trust_pool file … } }`). The global (shared) AOP
   certificate is rejected: it proves "from Cloudflare", not "from our
   account".
3. **New address**: the current IP (203.0.113.10) is in public DNS history.
   Hostinger documents no self-serve IP change: ask support first; otherwise
   provision a fresh VPS and move with `release.sh` + database and Garage
   restore. Done last (R18 step 6) and may slip without blocking lots 2–4;
   layers 1–2 already make the old IP useless for application traffic.

**Rationale**: Layer 1 sheds junk before it reaches the VM; layer 2 stops
attackers using their own Cloudflare account to reach our origin; layer 3
reduces exposure to volumetric floods on the raw IP.

**To verify**: Hostinger firewall rule count is enough for ~22 CF ranges
(quickstart V2); zone-level AOP certificate is presented for custom hostnames
(V2).

## R5 — Real visitor address (FR-007)

**Decision**: Caddy global options:
```
servers {
	trusted_proxies static <Cloudflare ranges>
	trusted_proxies_strict
	client_ip_headers CF-Connecting-IP
}
```
and `header_up X-Real-IP {client_ip}` (instead of `{http.request.remote.host}`).
The admin/GrowthBook matcher becomes `client_ip` (instead of `remote_ip`).
The Cloudflare ranges live in one generated snippet
`infra/deploy/cloudflare-ips.caddy` (imported by the Caddyfile), produced by
`infra/cloudflare/refresh-ips.sh` from `https://www.cloudflare.com/ips-v4|v6`,
which also prints the firewall list for R4.

The renderer is unchanged: `api/leads/route.ts` already trusts only
`X-Real-IP`.

**Rationale**: `CF-Connecting-IP` is the only client-IP header Cloudflare does
not let a visitor forge, and Caddy only honours it from a trusted peer.

**Alternatives**: `caddy-cloudflare-ip` module (auto-refresh; one more
third-party module in the custom build for ranges that change a few times a
year — rejected for Simplicity First); `X-Forwarded-For` (spoofable first hop).

## R6 — Admin and GrowthBook restriction at the edge (FR-008)

*Superseded by 019-admin-access (2026-10-16): Cloudflare Access replaces the address rule (019 research R1, R2, R9).*

**Decision**: one WAF custom rule: block when host is the admin or a
GrowthBook host **and** `ip.src` is not in the IP list `trefle_admin`, whose
content is generated from `ADMIN_ALLOWED_IPS` by the apply script. Caddy keeps
its own check (now `client_ip`, R5).

**Note for the switch**: the production `ADMIN_ALLOWED_IPS` is currently wide
open (open item since 003). The restriction is only as good as that value —
the switch checklist asks for the real list. Cloudflare Access (Zero Trust,
free ≤ 50 users) is the better answer for editors on changing networks;
recorded as a follow-up, out of lot 1.

**Update 2026-10-11**: T025 (setting the real list) is moved to its own
feature, 019 — admin access, which re-decides between an IP list and
Cloudflare Access. Until it ships, FR-008 is met by the mechanism only, not
by the value.

## R7 — Lead-form rate limit at the edge (FR-005)

**Decision**: the Free plan's single rate-limiting rule: `POST` to
`/api/leads`, counted per IP, 10-second window (fixed on Free), **5 requests**
→ block for 10 s. The app's own limits (10/min, 100/day per IP) stay.

**Rationale**: A human submits once; 5 per 10 s from one IP is already abuse,
and blocks at the edge before the origin pays for it.

## R8 — Page HTML is not cached (FR-009)

**Decision**: Cloudflare does not cache HTML by default and the renderer sends
`private, no-store`. Belt and braces: a Cache Rule **bypass** for every page
host except `/_next/static/*` (which stays cached by default: hashed, `public,
immutable`). This rule is what lot 3 will replace.

## R9 — Image cache at the edge (FR-011)

**Decision**: Cache Rule on the image host: *eligible for cache*, *respect
origin TTL* (imgproxy sends `public, max-age=31536000`), **Vary on `Accept`**
with action *normalize* and `media_types: ["image/webp"]`, so the cache keeps
exactly two variants (WebP / not). Polish off.

**Rationale**: imgproxy URLs have no file extension, so Cloudflare would not
cache them by default. imgproxy's own guidance: include `Accept` in the cache
key when format negotiation is on (`IMGPROXY_ENFORCE_WEBP=true`), disable CDN
image optimisation.

**Fallback** (if the Vary rule misbehaves in V5): set imgproxy to always output
WebP for everyone (all supported browsers), drop `Vary`.

## R10 — Asset host caching (FR-012)

**Decision**: Caddy adds `Cache-Control: public, max-age=31536000, immutable`
on the asset host, plus a Cache Rule *eligible for cache / respect origin TTL*.
Safe only because asset keys are never reused (R11).

## R11 — Media and font keys are never reused; replaced media keep working (FR-013, FR-014)

**What the code does today** (Payload 3.88, read in
`payload/dist/uploads/generateFileData.js`, `getSafeFilename.js`,
`collections/operations/utilities/update.js`):
- The object key is the sanitised filename (`payload.config.ts`
  `generateFileURL`). Replacing the file of an existing media document picks a
  new name (the old one still exists in the DB at that point, so `photo.jpg`
  becomes `photo-1.jpg`) and **deletes the old object**.
- Page HTML (GrapesJS) references images **by URL**, not by media id
  (`imgproxy.ts` rewrites `<img src>` and CSS `url()` under `ASSET_ORIGIN`).
- ⇒ **Existing defect**: replacing a media file breaks every page still
  pointing at the old URL (old object deleted). And a freed name can later be
  taken by a different upload, so a long-cached old image could be served for
  it.

**Decision**:
1. **Unique keys**: a `beforeOperation` hook on `media` and `fonts` renames the
   incoming file to `<base>-<hash8>.<ext>` (first 8 hex chars of the file's
   SHA-256). New keys can never collide with a freed or legacy key.
2. **Alias on replacement**: a hidden, read-only `previousFilenames` field on
   `media`; a `beforeChange` hook appends the old filename when the filename
   changes.
3. **Alias map**: CMS endpoint `GET /api/media/aliases` returns
   `{ oldKey: currentKey }` for all media with previous filenames (chains
   resolved to the final key). Renderer fetches it once, cached with tag
   `media-aliases`; `rewriteImageTags`, `rewriteBackgroundUrls` and a new
   `rewriteAssetLinks` (for `href` to PDFs under `ASSET_ORIGIN`) substitute
   the current key before signing.
4. **Refresh**: `afterChange`/`afterDelete` on `media` revalidate
   `media-aliases` through the existing `revalidateTags` path → pages pick up
   the new key on the next request (lot 1 renders every request), well inside
   FR-014's minute. Lot 3 adds the edge purge.

**Rationale**: Fixes the existing defect and makes every image/asset URL
content-addressed in practice, so 1-year caching is safe everywhere without
any purge on the normal path.

**Alternatives**:
- *imgproxy `cachebuster` (`cb:`) with a per-key version* — still needs a
  key→media lookup and does not fix references to deleted keys.
- *Rewrite page HTML on replacement* — mutates published content and its
  versions/drafts from a hook; risky and hard to undo.
- *Purge on replacement* — does not prevent key reuse, and image purges are
  hostname-wide (R12).

## R21 — Usage warning before replacing an image (FR-020, FR-021)

**Decision**:
- **Usage lookup** `lib/media-usage.ts`, exposed as
  `GET /api/media/:id/usage` (admin or editor — same as `media.update`):
  pages whose `builder.html` or `builder.css` contains `/<key>` for the
  current filename or any `previousFilenames` (Payload `contains` on the two
  text fields), plus pages whose `seo.ogImage` is the media id, plus domains
  whose `branding.defaultOgImage` is the media id or whose `branding.faviconUrl`
  contains `/<key>`. Returns title, domain
  hostname, path, status, variant marker and admin URL per page. Same shape of
  solution as `endpoints/domainFontUsage.ts` (015).
- **Panel** `MediaUsage.client.tsx` in `admin.components.edit.beforeDocumentControls`
  on `media` (the slot already used on Pages and Domains): « Utilisée dans :
  … » / « Cette image n'est utilisée dans aucune page. », first 20 entries then
  « et N autres » expandable; loading and error states.
- **Confirmation** `MediaReplaceConfirm.client.tsx`: a custom save control
  for `media` that, when the upload field holds a new file **and** usage is
  non-empty, opens a modal — « Attention, l'image que vous voulez remplacer est
  utilisée dans ces pages : … La nouvelle image apparaîtra dans toutes ces
  pages. Pour ne changer qu'une page, ajoutez plutôt une nouvelle image et
  choisissez-la dans cette page. » — with « Remplacer partout » / « Annuler ».
  Otherwise it behaves as the default save. Exact Payload slot (custom
  `SaveButton` vs. wrapping the form submit) is confirmed against the Payload
  3.88 admin docs at implementation; the behaviour above is the contract.

**Rationale**: Matching on `/<key>` with keys that now carry a content hash
(R11) makes false positives negligible; including previous keys catches pages
not re-saved since a replacement. Computing on demand avoids a usage index to
keep in sync (Simplicity First).

**Alternatives**: a stored page↔media index updated by page hooks (more
moving parts, drift risk); warning only after save (too late — the user asked
for the warning *before* overwriting); blocking replacement of used images
(prevents the legitimate "change it everywhere" case, e.g. a logo).

## R22 — Deleting a used image is blocked (FR-022)

**Decision**: a `beforeDelete` hook on `media`
(`hooks/media-delete-guard.ts`) runs the same usage lookup (R21) and, when
`total > 0`, throws a Payload `APIError` (409) with the French message
« Impossible de supprimer cette image : elle est utilisée dans N page(s) :
A, B, C… Retirez-la de ces pages ou remplacez son fichier, puis réessayez. »
Payload runs `beforeDelete` per document, so a bulk delete refuses only the
used items. Server-side, so it also holds for the API and the list view. The
usage panel adds « La suppression est bloquée tant que l'image est
utilisée. »

The two import cleanups (`jobs/pageImport.ts` `deleteImportedMedia`,
`jobs/siteImport.ts` `deleteCreated`, which deletes the import's pages first)
pass `context: { allowUsedMediaDelete: true }`; the hook skips the check only
then.

**Alternatives**: a confirmation listing the pages (rejected by the user:
block); access-control `delete` returning false (no explanatory message,
silently hides the action).

## R12 — Image take-down (FR-015)

**Decision**: documented operator procedure + script
`infra/cloudflare/purge-media.sh <key>…`: remove the file from storage —
**unused** image: delete it in the admin; **used** image (deletion is blocked,
R22): replace its file with the corrected or a neutral image (confirmation
R21; Payload deletes the old object and pages show the new file through the
alias map) — then purge every old key's asset URL by URL and the image host
**by hostname**.

**Rationale**: imgproxy URLs start with the signature, so neither prefix nor
tag purge can target one source; hostname purge is coarse (every image is
re-processed once) but this is a rare, deliberate action.

## R13 — Request size and duration limits

- Cloudflare Free/Pro cap request bodies at **100 MB**; the Penpot import
  accepts 100 MB + multipart slack (`siteImportAnalyse.ts`,
  `SiteImportWizard.client.tsx`). **Decision**: lower `MAX_PENPOT_FILE_BYTES`
  (server and client) to **95 MB**; reference files are ~2–15 MB.
- Proxied requests time out after ~100 s without response. Long work already
  runs as Payload jobs (`page-import`, `site-import`, 202 responses); the
  leads CSV export streams. No change.

## R14 — Cloudflare features that touch HTML/JS (FR-006, FR-010)

**Off**: Rocket Loader, Email Address Obfuscation, Automatic HTTPS Rewrites,
Polish, **Bot Fight Mode** (its JS detections inject a script and would also
challenge the Playwright e2e run of SC-002; L3/L4/L7 DDoS mitigation is
independent and always on). **On**: Always Use HTTPS, TLS ≥ 1.2, Free managed
ruleset, Browser Integrity Check (default). HSTS stays set by Caddy.
Revisit Bot Fight Mode in lot 3, where the Worker owns the nonce.

## R15 — Configuration as code (FR-018)

**Decision**: `infra/cloudflare/` holds declarative JSON (zone settings,
rulesets per phase, cache rules, IP list) and `apply.sh` (bash + `curl` +
`jq`), idempotent: `PATCH` zone settings, `PUT` each ruleset phase entrypoint
(replaces the phase wholesale), upsert the IP list. `add-client-domain.sh`
creates a custom hostname and prints the two records the client must add.
Tokens in `infra/.env` (git-crypt): `CLOUDFLARE_ZONE_ID`,
`CLOUDFLARE_API_TOKEN` (zone settings/rules/cache purge/custom hostnames),
`CLOUDFLARE_DNS_TOKEN` (DNS edit only, used by Caddy) — least privilege.

**Alternatives**: Terraform/OpenTofu provider (a new tool plus state to store
and protect — rejected for Simplicity First at this size); dashboard only
(not reproducible, violates FR-018).

## R16 — Load testing (SC-006)

**Decision**: k6 (`grafana/k6` container, run from a machine outside the
VPS; a dev tool, not a runtime dependency). Scenarios in
`infra/loadtest/`: page views on a dedicated test page, image fetches, a
light lead-submission stream to a test domain. Baseline before the switch,
re-run after. Origin hits counted from Caddy access logs. Run off-peak; the
load-test source IP is added to a temporary WAF *skip* rule for rate limiting.

**Expectation**: page-view throughput is bounded by the VPS in lot 1
(no regression is the bar); images/fonts must not reach the origin beyond the
first request per file at the target volume.

## R17 — Moving `client-site.example` to `www.` (FR-016a)

The renderer emits **no canonical tag and no sitemap** today (checked:
no `alternates`/`metadataBase`/sitemap route in `apps/web/src`). FR-016a
therefore reduces to: rename the Domains record hostname to
`www.client-site.example` (its cache tags follow the hostname),
replace the root in `WEB_HOSTNAMES`, add the custom hostname, and set the
registrar forwarding (path + query preserved — V9).

## R18 — Switch sequence and rollback (FR-017, SC-007)

1. **Ship code first** (no Cloudflare needed): unique keys + aliases (R11),
   asset `Cache-Control` (R10), Penpot cap (R13), custom Caddy image still
   using its current issuance.
2. **Zone** to Cloudflare, all records DNS-only (R1); verify mail.
3. **Apply config** (R15), AOP cert, DNS-01 delegation records; test through a
   proxied `cf-check.example.com` host.
4. **Switch Trefle hosts**: `trusted_proxies` (already harmless while
   direct) and DNS-01 issuance deployed first; constitution amended; hosts
   turned to proxied; **only then** AOP `client_auth` (enabling it while
   traffic is still direct would refuse every visitor); then the Hostinger
   firewall.
5. **Client domain**: custom hostname, client CNAMEs, Domains rename, root
   forwarding.
6. **New IP** (R4.3).

**Rollback** (< 15 min): set records to DNS-only (grey cloud), redeploy the
previous Caddyfile (no `client_auth`), open 80/443 in the firewall. Client
`www.` hosts need their CNAME switched back to an A record — documented,
slower, hence step 5 only after 4 has been stable. After the IP change
(step 6), grey cloud would publish the new IP and undo FR-003: roll back the
Caddy/firewall change while staying proxied where possible, and plan a further
IP change if grey cloud was used.

## R19 — GDPR (FR-019)

Cloudflare becomes a processor (self-serve DPA is part of its terms; US
transfers under the Data Privacy Framework). Update the legal-notice page
content and the processing register (outside the repo); no cookie is added in
lot 1 (Bot Fight Mode off, so no `__cf_bm`).

Adds an edge layer to the Architecture and two runtime additions beyond the
